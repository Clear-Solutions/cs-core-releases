# Создание проекта агентом

## Результат

По описанию идеи агент готовит подходящий стек, приватный репозиторий, воспроизводимый запуск, первый рабочий этап, тесты и CI; подключает проект к каталогу и планированию. Шаблон FastAPI — доступная основа, а не обязательный стек. Для иной архитектуры агент создаёт минимальную основу и переносит общие правила, не притягивая задачу к шаблону.

## Сначала определить продукт и платформы

Запрос «проект», «сервис» или «калькулятор» не задаёт тип продукта. До реализации
должны быть известны формат и целевые платформы. Если пользователь их не указал,
обязательно спросите, а не выбирайте веб-сайт автоматически. Возможны веб-страница,
веб-приложение/PWA, desktop, mobile, CLI, API, бот, расширение, библиотека,
автоматизация без UI или комбинация. Предлагайте только релевантные варианты.

Для приложения уточните конкретные системы/устройства: Windows/macOS/Linux,
Android/iOS, браузеры, необходимые сочетания и приоритет первого выпуска.
«Кроссплатформенный» — не список целей: уточните требуемые платформы и их различия.
Также выясните способ распространения: ссылка, установщик, магазин приложений,
пакет/библиотека, интеграция или внутренний запуск. Один код для нескольких платформ
не означает, что артефакты сборки, UX и тесты на каждой платформе одинаковы.

Пока обязательная информация о формате/платформах не получена, не начинайте
продуктовую реализацию, не создавайте репозиторий под угаданный стек и не выпускайте
домен/приложение. Продолжайте независимую диагностику доступов, изучение требований
и сравнение архитектур. Исключение — явное поручение пользователя предложить и
реализовать формат самостоятельно; зафиксируйте этот выбор и его основания.
Известные ответы не переспрашивайте; отсутствие ответа не означает согласия.

### Независимость продукта

Новые продукты по умолчанию имеют собственный интерфейс и идентичность.
Принадлежность репозитория организации Clear-Solutions не разрешает добавлять
Clear Solutions, её логотип, слоган, Telegram или фирменные элементы в интерфейс,
загрузочный экран, иконку, onboarding либо дистрибутив. Брендинг команды добавляется
только по явному запросу. Если имени/бренда продукта нет, используйте нейтральное
рабочее название и спросите о желаемом оформлении, когда это существенно.
Служебные AGENTS, политика, CODEOWNERS и каталог могут указывать команду.
Внутренние идентификаторы сборки также не становятся публичной идентичностью.

### Критерии для разных платформ

В `docs/project-brief.md` укажите тип продукта, список поддерживаемых платформ и версий,
целевой первый сценарий, способы ввода, offline/network, хранение/синхронизацию,
интеграции, приватность, распространение и UX/доступность — только то, что относится
к продукту. Разделяйте обязательные требования, допущения и открытые вопросы.
Для каждого целевого варианта задайте проверку сборки, запуска и первого сценария.
Не объявляйте Windows/iOS/Android поддержку на основании одного браузерного теста.
Если целевая среда недоступна, обозначьте непроверенный вариант и конкретный план
его проверки. Стек, общие компоненты и платформенный код выбираются после ответов.

Подробные вопросы по форматам: [интервью](project-intake.md); итог: [шаблон brief](../templates/project-brief.md).

## Предпроектное интервью

Перед реализацией агент проверяет, достаточно ли сведений для качественного первого этапа.
Если нет — сам задаёт 3–5 наиболее важных вопросов в первом раунде. Не выдавайте
пользователю длинную анкету и не спрашивайте заново уже известное. В первом раунде приоритетны неизвестные формат и платформы. Уточняйте цель
и пользователей, первый сценарий/критерии приёмки, данные и интеграции, интерфейс,
ограничения и площадку. Второй короткий раунд нужен только для существенных пробелов.
Выбор языка и библиотек агент делает сам; предлагает варианты с понятными последствиями,
когда речь о продуктовом решении, которое должен принять пользователь.

Сохраните `docs/project-brief.md`: известные требования, проверяемые критерии,
ограничения, допущения и открытые вопросы. Критичные неизвестные (например,
поставщик API, права на данные или целевая production-среда) не заменяйте догадками.
Пока ждёте ответы, продолжайте независимое изучение и подготовку. Уже согласованные
требования и разрешения сохраняются; отдельное одобрение каждого документа или
рутинного технического решения не требуется.

Если пользователь просит только выяснить доступы, выполняйте диагностику по
`cs-core-hub/docs/access-check.md` в режиме чтения: не создавайте репозитории,
не выдавайте права, не приглашайте людей и не меняйте production. Отличайте
подтверждённые права от неизвестных и необходимых позже. Не просите секреты в чат.

Готовые сценарии агентов: [cs-core-skills](https://github.com/Clear-Solutions/cs-core-skills). Для неподготовленной рабочей папки используйте `cs-workspace-setup`; не устанавливайте нерелевантные скиллы автоматически.

## 1. Требования и архитектура

Изучите запрос, каталог hub и закреплённую общую политику. Опишите пользователей, сценарии первого этапа, входные/выходные данные, интеграции, среду и критерии приёмки. Используйте уже известные условия. Задавайте только вопросы, которые существенно влияют на реализацию; остальные решения принимайте самостоятельно и явно фиксируйте допущения. Не изобретайте нагрузку, SLA, сроки, бюджет или согласие на обработку данных.

Выберите минимальную достаточную архитектуру: язык, runtime, UI/API, хранение, фоновые задачи и поставка. Не добавляйте БД, очередь, vector store, LLM SDK или микросервисы без конкретного требования. Для значимого выбора сравните разумные альтернативы и запишите ADR `docs/decisions/0001-stack.md`. Для простого решения достаточно короткого обоснования; отдельный этап согласования обычного стека не требуется.

## 2. Подбор библиотек

Агент самостоятельно подбирает необходимые зависимости. Для каждой укажите решаемую задачу, категорию runtime/dev, выбранную совместимую версию и ссылку на официальную документацию. Проверяйте актуальные API, поддержку выбранного runtime, состояние поддержки, лицензию, известные уязвимости и сложность эксплуатации. Не считайте число stars или самую свежую версию достаточным основанием. Официальные release notes, package registry и advisory базы дополняют документацию.

Не используйте несуществующие пакеты или неподтверждённые API. При недоступном источнике обозначьте ограничение, не заявляйте проверку, которой не было. Применяйте стандартную библиотеку, если её возможностей достаточно. Разделяйте runtime/dev и закрепляйте прямые/транзитивные зависимости штатным lockfile. Устанавливайте их в изолированном окружении; не меняйте глобальные пакеты сервера.

Запишите зависимости и источники в `docs/dependencies.md`: пакет, назначение, категория, основание выбора и официальная ссылка; версии читаются из lockfile, не дублируются в расходящейся таблице. Обновления зависимостей проходят PR с проверкой совместимости, security и изменений поведения.

Рутинные бесплатные библиотеки не требуют отдельного подтверждения. Если решение создаёт новые расходы, передаёт данные внешнему провайдеру или меняет рабочую инфраструктуру, проверьте существующее разрешение и ограничения задачи. Запросите только недостающие сведения или разрешение перед зависимым действием, продолжая независимую подготовку. Не запрашивайте повторно уже полученное разрешение.

## 3. Репозиторий и рабочая основа

После выбора границ проекта создайте `Clear-Solutions/cs-project-<назначение>` с private visibility и проверьте приватность чтением API. Если имя занято, не меняйте чужой репозиторий: проверьте, относится ли он к задаче, и выберите ясное свободное имя при необходимости. Доступ: владелец elementary1997, согласованный разработчик/ревьюер light2217. Другие пользователи получают доступ только по отдельному указанию владельца.

Если подходит FastAPI/Python, используйте service-template. Иначе создайте основу выбранного стека и перенесите подходящие AGENTS, Cursor rules, CODEOWNERS, PR/Issue templates, правила безопасности и pin политики. Не переносите Python-команды, Dockerfile или чужие доменные ограничения в несовместимый стек. Все команды проекта должны быть реальными и проверенными.

README, AGENTS.md, CONTRIBUTING.md, SECURITY.md, `.env.example`, lockfile, CI, документация решений и `.clear-solutions/project.json` входят в первый импорт. Предоставьте локальную копию закреплённой политики с manifest для работы без GitHub-доступа. Включите связанные файлы (в том числе templates/project-brief.md), проверьте локальные ссылки и хеши. Первоначальный импорт в пустой main — bootstrap-исключение; дальнейшие изменения только в ветках/PR с независимым ревью. Не выдавайте bootstrap за человеческое одобрение.

Проверьте доступность GitHub protection по тарифу и примените согласованную конфигурацию, когда это поддерживается. Free private main не защищена технически; зафиксируйте ограничение. Наличие файлов не подтверждает enforcement.

## 4. Первый рабочий этап и подключение

Реализуйте один полный сценарий с измеримыми критериями. Используйте временные данные; демо и заглушки помечайте явно. Тестируйте ошибки, валидацию, авторизацию и ограничения внешних интеграций там, где это относится к сценарию. Для AI-функций добавьте небольшую оценочную выборку и проверку отказов провайдера; не выдавайте mock за реальный вызов.

Добавьте компонент в `hub/catalog.json` через PR: назначение, ответственный, lifecycle и реальный URL, если он есть. Создайте необходимые Issues с критериями приёмки и добавьте их и PR в приватный Project Delivery. Сроки не выдумывайте. Создавайте задачи только для известного объёма работ, не размножайте одно действие во всех репозиториях. Карточку showcase добавляйте, когда проект готов к показу и это входит в запрос.
При этом применяйте [правила публикации](showcase-publication.md) и cs-showcase-publish:
каждый новый проект получает единое превью, доступное интерактивное демо и проверку
стандартов/UI; simulation обозначается отдельно от реального продукта.

## 5. Проверки и доставка

Проверьте setup/run/check/security из чистой копии без production credentials; необходимые зависимости и доступ к package registry опишите явно. Запустите первый сценарий и проверьте CI на GitHub. Workflow actions закрепляйте SHA; PR не получает production secrets. Для UI выполните требования development.md.

Подготовьте CD для выбранной среды: точный проверенный main SHA или неизменяемый artifact, проверка здоровья/ревизии и документированный откат. Активация требует конкретного окружения и настроенных credentials. Если среды нет, поставьте задачу, подготовьте конфигурацию и явно сообщите, что production CD ещё не работает. Не создавайте пустой успешный deploy-job.

## Отчёт

При изменении назначения, структуры, возможностей, платформ, команд, доступов или CI/CD обновляй README затронутого репозитория. Если меняются общие связи, промпты или подготовка участника — обновляй также каталог/документацию Hub и README организации (.github-private/profile/README.md) в пределах задачи. Сверяй инструкции с фактическим состоянием; не объявляй подготовленные настройки работающими. Если README не затронут, укажи это с причиной в PR.

Дайте ссылки на репозиторий, PR и Project, обоснование стека, фактически выполненные проверки и их результаты. Отдельно укажите работающую функциональность, подготовленные настройки, ожидаемое человеческое ревью и реальные блокеры. Не утверждайте, что проект готов к production до подтверждённого выпуска, health и восстановления/отката.

## Совместимость агентов

Каждый новый проект должен поддерживать Codex, Cursor, Claude Code и Google Antigravity.
Создай корневой AGENTS.md, Cursor alwaysApply-правило со ссылкой @AGENTS.md,
CLAUDE.md с отдельной строкой @AGENTS.md и .agents/rules/project.md с YAML
trigger: always_on и ссылкой @../../AGENTS.md. Проверяй эти входы в CI.
