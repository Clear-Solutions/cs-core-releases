# Предпроектное интервью для разных продуктов

Агент читает уже известные условия и спрашивает только недостающие сведения.
Первый раунд — 3–5 важных вопросов с короткими понятными вариантами; последующие
вопросы зависят от ответов. Если формат или платформы неизвестны, это обязательные
вопросы до реализации. Если пользователь поручил выбрать формат самостоятельно,
зафиксируйте это поручение и обоснование выбранного варианта.

## Первый раунд

1. Что создаём: веб/PWA, desktop, mobile, CLI, API, бот, расширение, библиотеку,
   автоматизацию без UI или комбинацию? Предлагайте варианты под конкретную идею.
2. Где продукт должен работать: конкретные системы, устройства/архитектуры,
   браузеры или runtimes; что важно для первого выпуска?
3. Для кого он и какой первый сценарий должен работать от начала до конца?
4. Где живут данные, нужны ли offline/синхронизация, внешние интеграции и вход?
5. Как пользователь получает продукт и какие ограничения известны?

Не задавайте все пять вопросов автоматически. При известном формате/сценарии
сосредоточьтесь на реальных пробелах. Не требуйте технического словаря: объясните
варианты на примере пользователя. Рутинные технические решения принимает агент.

## Вопросы по выбранному формату

| Формат | Что уточнить, когда относится к задаче | Что проверить |
| --- | --- | --- |
| Веб-страница / веб-приложение | Статическая страница или интерактивный сервис, браузеры/устройства, вход, данные, hosting | Сборка, responsive/клавиатура/ошибки, целевые браузеры, первый сценарий |
| PWA | Нужна ли установка, offline, обновление, push и синхронизация; возможности целевых браузеров | Установка, offline/возврат сети, обновление, заявленные браузеры |
| Desktop | Windows/macOS/Linux и версии, x64/ARM, native-возможности, installer/portable, обновления и подпись | Артефакт и запуск на каждой заявленной ОС/архитектуре, первый сценарий, установка/обновление |
| Mobile | Android/iOS и версии, телефоны/планшеты, разрешения, offline, магазины или внутреннее распространение | Сборка для целей, эмулятор/реальное устройство, разрешения, жизненный цикл и сценарий |
| CLI | ОС/shell, ввод-вывод, automation/non-interactive, способ установки | Exit codes, stdin/stdout/stderr, ошибки, сценарий на целевых системах |
| API | Потребители, контракт/protocol, auth, данные и deployment | Контракт, ошибки, права, миграции и реальный клиентский сценарий |
| Бот | Канал/платформа, события, polling/webhook, права, интеграции | Обработка событий, ошибки провайдера, повторная доставка и сценарий |
| Расширение | Браузер/host-приложение, версии, нужные permissions и канал установки | Совместимость, пакет, разрешения и сценарий в целевом host |
| Библиотека | Потребители, язык/runtime/версии, API и registry | Установка пакета, совместимость, импорт/использование из независимого consumer |
| Автоматизация без UI | Триггеры, расписание/события, системы, права, повторный запуск и наблюдаемость | Реальный сценарий, безопасный retry/idempotency, ошибки и понятный результат |
| Несколько платформ | Точный список целей, общие/различные сценарии, приоритет релизов, данные/синхронизация | Матрица сборки и запусков; доказательства по каждой цели отдельно |

Это подсказки агенту, а не анкета для заполнения всех строк. Например, desktop-расширение
и мобильный бот могут требовать комбинацию строк. Не выбирайте один framework по
привычке: оцените UX, native API, размер, сопровождение, доступность toolchain и тестов.

## Итог интервью

Заполните [project brief](../templates/project-brief.md). Обязательное неизвестное
остаётся открытым вопросом и блокирует зависимую реализацию. Неизвестный бюджет,
нагрузка или platform support не становятся выдуманными числами. Во время ожидания
можно исследовать стек и доступы, не создавая продукт под неподтверждённый формат.

Отделяйте требования от рекомендаций агента. Не требуйте нового разрешения на
каждый выбор, если работа уже поручена; учитывайте принятые ответы и полномочия.
Продуктовые имя, логотип, ссылки и иконки самостоятельны. Clear Solutions
не добавляется в UI/дистрибутив по факту принадлежности GitHub-репозитория.

Проверки обозначаются точно: «собрано для», «запущено на», «сценарий проверен на».
Один успешный web-тест не подтверждает native-приложение или все платформы.
