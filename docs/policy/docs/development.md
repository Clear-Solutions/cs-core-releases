# Правила создания проектов

## До реализации

Опишите задачу, аудиторию, владельца продукта и измеримые критерии готовности. Выберите минимальную достаточную архитектуру. Запишите ограничения данных и внешних сервисов; демо не выдавайте за работающую интеграцию. Значимые архитектурные решения сохраняйте в `docs/decisions/`.

## Выбор стека и зависимостей

Агент самостоятельно подбирает минимальную архитектуру и библиотеки под задачу, проверяет официальные источники и совместимость, закрепляет зависимости и проверяет реальный запуск. Service template применяется только при соответствии требованиям. Подробный порядок — [создание проекта агентом](project-bootstrap.md).

## Состав репозитория

Обязательны README с воспроизводимым запуском, AGENTS.md, CONTRIBUTING.md, SECURITY.md, CODEOWNERS, PR template, CI, pipeline поставки, lockfiles и `.env.example` без реальных значений. Для существующего проекта сохраняются его обоснованные команды и архитектура. Общая политика подключается зафиксированным commit SHA; локальные инструкции могут усиливать, но не ослаблять её.

## Код и данные

Валидация записей выполняется на сервере. Авторизация, CSRF, ограничения загрузок и недопущение утечки приватных объектов проверяются тестами. Миграции данных обратимы или имеют документированный план восстановления. Тесты используют временные БД, без production-секретов. Зависимости фиксируются lockfiles, изменения рассматриваются в PR.

## UI

Для веб-интерфейсов проверяются ширины 320, 390, 768 и 1440 px, масштаб 200%, клавиатура, фокус и его возврат, reduced motion, пустые и ошибочные состояния, длинные имена, пагинация и загрузки. Отсутствие переполнения не означает качественную вёрстку: автор просматривает снимки затронутых экранов и описывает конкретные результаты. Формы и кнопки сохраняют доступность. Пользовательский текст соответствует правилам русского языка.

## Готовность PR

Критерии выполнены, обязательные CI проверки зелёные, собственная визуальная проверка проведена, документация актуальна. Указаны риски, миграции, проверка production и способ отката. Другой участник одобрил актуальную версию. Не допускаются отключённые проверки, фиктивные approvals или утверждения о проведённых проверках без результатов.

## Документация результата

При изменении назначения, структуры, возможностей, платформ, команд, доступов или CI/CD обновляй README затронутого репозитория. Если меняются общие связи, промпты или подготовка участника — обновляй также каталог/документацию Hub и README организации (.github-private/profile/README.md) в пределах задачи. Сверяй инструкции с фактическим состоянием; не объявляй подготовленные настройки работающими. Если README не затронут, укажи это с причиной в PR. См. [порядок обновления README](readme-maintenance.md).
