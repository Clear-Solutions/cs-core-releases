# Обязательная CI/CD

## CI

Каждый PR в `main` и каждый commit `main` запускают неизменяемо названные jobs `checks` и `security`. Jobs не должны пропускаться из-за фильтра paths. Проверки включают форматирование, lint, meaningful tests, сборку для используемого стека, security scan и аудит зависимостей. Веб-проекты дополнительно проверяют UI, сценарии публикации, фотографии, доступность и пагинацию в изолированной БД.

Перед включением required checks убедитесь, что их имена и источник GitHub Actions совпадают с фактически завершёнными jobs. Зелёный job без исполнения обязательных команд не считается CI. Workflow и изменение security exclusions сами рассматриваются через PR.

## CD приложений

Поставка запускается после успешного CI для **точного SHA из `main`**. Production не является required check до merge: это создало бы круговую зависимость. PR не получают production secrets. При использовании `workflow_run` проверяются conclusion=success, исходное событие=push, head_branch=main и исходный repository.

Production job использует environment `production`, единственную concurrency group без отмены работающего выпуска, проверенный host key и отдельный restricted deploy credential. Секреты обязательны: отсутствующая конфигурация завершает job ошибкой. SHA проходит строгую валидацию. На сервере нельзя исполнять произвольную строку SSH_ORIGINAL_COMMAND.

До запуска сервиса сохраняется предыдущая версия и проверяется схема данных. Выпускается подготовленный artifact или новая release-директория, `.env` и данные остаются за её пределами. После переключения проверяются health endpoint и ключевой read-only сценарий. При ошибке возвращается предыдущая версия; destructive migration требует отдельного плана восстановления. Результат поставки фиксируется SHA, временем и статусом health check.

## CD этого репозитория

`delivery.yml` после успешного Policy CI для `main` упаковывает `git archive` конкретного коммита, создаёт manifest SHA-256 и доставляет версионированный GitHub Actions artifact. Production credentials не нужны. Проекты принимают новую версию правил отдельным PR, вместо незаметного обновления из плавающего `main`.

## Проверяемый контракт проекта

Каждый сервис документирует команды `setup`, `check`, `security`, `build` (если требуется), `deploy`, `health` и `rollback`; наличие Makefile цели без реализации не считается поставкой. В `.clear-solutions/project.json` фиксируются policy commit, команды проверки, workflow и health URL. Новые проекты нельзя объявлять готовыми, пока реальный pipeline и его успешный запуск не проверены.
