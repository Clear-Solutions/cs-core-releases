# Подготовка рабочего каталога организации

Этот промпт готовит **среду участника**, а не создаёт продукт. Он подходит для нового
каталога и существующей рабочей папки, для Codex, Cursor, Claude Code, Antigravity
и других агентов с доступом к файлам. Каждый участник использует собственный GitHub-аккаунт.
Клиент без терминала может подготовить инструкции, но не должен объявлять настройку выполненной.

Скопируйте блок целиком. Достаточно указать каталог; остальные неизвестные сведения
агент уточнит только при необходимости. Путь должен вести в выделенную рабочую папку,
а не в домашний каталог, корень диска или папку с несвязанными проектами.

## Промпт

```text
Подготовь рабочий каталог для работы в организации GitHub Clear-Solutions.
Это настройка среды участника, а не запрос на создание нового продукта.

Каталог: [абсолютный путь; если не указан — предложи выделенную папку].
Мой GitHub-логин: [если неизвестен — определи через авторизованный API].
Агент: [Codex / Cursor / Claude Code / Antigravity / другой].
Рабочие репозитории: [список или «выберем позже»].

1. Сначала установи границы работы.
Прочитай применимые AGENTS.md и клиентские инструкции в текущем каталоге,
родительских папках и существующих checkout. Проверь git status, origin и тип папки.
Не перезаписывай инструкции, незакоммиченные изменения или чужие репозитории.
Если выделенный корень не известен или содержит несвязанные проекты, уточни путь.
Не создавай общий Git-репозиторий поверх нескольких checkout и не добавляй submodules.
Не меняй глобальную конфигурацию Git, клиенты, системные пакеты или production.
Учти уже известные ответы и разрешения; не задавай повторные вопросы.

2. Проверь доступы без изменения удалённого состояния.
Проверь наличие Git и доступного GitHub API/CLI/коннектора, авторизованный логин,
членство и роль в Clear-Solutions, доступ к cs-core-standards, cs-core-hub, выбранным проектам
и Delivery (https://github.com/orgs/Clear-Solutions/projects/1).
Проверь разрешение участникам создавать приватные репозитории, если оно видно API.
Различай права аккаунта, разрешения используемого токена/приложения и Git-транспорт:
успешный SSH не доказывает доступ API, Read одного репозитория — Write другого,
а Write репозитория — возможность создавать репозитории или редактировать Project.
Отмечай pending-приглашения, недостаток прав и «не проверено» отдельно.
Не проверяй Write пробным push или созданием тестового объекта.
Не выводи токены, ключи, cookie, содержимое credentials или секретных .env.
Если нужна авторизация, предложи штатный вход от имени участника; не проси секреты
в чат, не заимствуй аккаунт владельца и не добавляй токен в URL origin.
Не выдавай права, не приглашай пользователей, не меняй защиту или видимость GitHub.
Составь конкретный запрос владельцу при недостатке прав, но не отправляй его.

3. Подключи источники правил.
Проверь https://github.com/Clear-Solutions/cs-core-standards и
https://github.com/Clear-Solutions/cs-core-hub. При доступе клонируй отсутствующие репозитории
в отдельные соседние каталоги cs-core-standards и cs-core-hub. Существующие checkout не
сбрасывай и не переключай принудительно; проверь origin, ветку и локальные изменения.
Недоступные приватные репозитории не подменяй выдуманной копией правил.
Можно подготовить минимальную памятку и список блокеров; настройка в этом случае частичная.
Service-template и продуктовые репозитории клонируй только по необходимости,
после проверки назначения и доступа; не копируй все проекты автоматически.
Для новой чистой копии получи правила из origin/main и запиши фактический commit SHA.
Для существующего проекта используй pin в .clear-solutions/project.json и локальный
snapshot/manifest: не обновляй политику на плавающий main без отдельного изменения.
Прочитай AGENTS.md, README.md, docs/git-policy.md, docs/security.md, docs/ci-cd.md,
docs/agents.md и docs/workspace-bootstrap.md в standards, а также AGENTS.md,
docs/access-check.md, docs/new-project.md и каталог в hub.
Рабочая памятка ссылается на источники и SHA; она не заменяет общую политику.
Если закреплённые версии отличаются или есть конфликт правил, укажи его;
не ослабляй требования и не обновляй pin/snapshot самовольно.

4. Настрой инструкции в выделенном корне.
Подготовь короткий AGENTS.md: карта локальных каталогов и источников политики,
правила выбора checkout, работы с незакоммиченными изменениями, ветками/PR,
секретами, проверками и отчётностью. Не копируй всю политику в четыре разных файла.
Codex использует AGENTS.md; для Cursor подготовь .cursor/rules/organization.mdc
с alwaysApply: true и @AGENTS.md; для Claude Code — CLAUDE.md с отдельной строкой
@AGENTS.md; для Antigravity — .agents/rules/project.md с YAML trigger: always_on
и ссылкой @../../AGENTS.md. Для другого клиента найди поддерживаемый способ
подключения по его официальной документации, не выдумывай формат.
Существующие инструкции дополняй согласованно; в Git-checkout такие изменения
проходят обычный PR. Инструкции корня не должны подменять проектные AGENTS.md,
закреплённую политику и реальные команды конкретного проекта.
Не считай наличие файла подтверждением того, что клиент его загрузил:
проверь доступным способом или попроси участника открыть папку в клиенте
и подтвердить обнаружение правил. Не запускай другие агенты и не устанавливай
их приложения/плагины только ради настройки файлов.

5. Зафиксируй обязательный рабочий процесс.
До изменения кода выбери один checkout, прочитай его инструкции и git status.
Работай в собственной feature-ветке, например feat/<login>/<task>, и пушь только её.
В existing main не делай прямой push, force push, удаление ветки или обход ревью.
Создай PR в main с описанием результата, проверок и ограничений.
Нужны одно независимое человеческое одобрение, успешные checks и security,
закрытые обсуждения и одобрение последнего изменения другим участником.
Ревьюеры команды — elementary1997 и light2217; автор не одобряет собственный PR.
Проверь актуальность ветки относительно main и применимые CODEOWNERS.
AI-ревью не заменяет человеческое; не нажимай merge до выполнения требований.
Используй предусмотренный политикой squash merge после проверок и ревью.
Первоначальный импорт в новый пустой репозиторий — отдельное bootstrap-исключение,
а не разрешение пушить main существующих проектов.
Временное разрешение владельца относится только к указанному участнику и объёму
работ текущего поручения: не переноси его на Иру, других агентов или будущие задачи
и не записывай как постоянное исключение в AGENTS.md.

Проверь main/protection/rulesets доступным API. Отдельно перечисли требования
организации и то, что GitHub реально обеспечивает. На Free для private репозиториев
защита может быть недоступна: не называй её включённой по файлу конфигурации.
Даже если прямой push технически разрешён, агент соблюдает процесс ветка → PR.
Локальные hooks могут быть дополнительной проверкой, но обходятся и не заменяют
серверную защиту. В рамках этого запроса не устанавливай hooks, не меняй тариф,
не ослабляй правила и не делай репозитории публичными.

6. Проверь готовность без лишних изменений.
Подготовь локальный WORKSPACE.md с картой каталогов, источниками и SHA, порядком
ветка → PR → ревью → CI, реальными командами каждого выбранного проекта и таблицей
доступов: действие | требуемое право | подтверждено/pending/не проверено | следующий шаг.
Не помещай туда секреты, аккаунтные данные или копии production-конфигурации.
Личный отчёт диагностики и локальные настройки держи вне Git-репозиториев;
если рабочий корень уже Git-checkout, выбери отдельное место для личного отчёта.
Не переноси runtime-зависимости продукта в standards/hub и не выбирай стек до идеи.
При подключении существующего проекта проверь локальный policy manifest и
клиентские входы штатной командой (например make agents, только если она существует).
Setup/check/security запускай по инструкции проекта в изолированной среде
при необходимости проверки готовности; не используй production-данные и credentials.
Не запускай deploy и не создавай продукт, PR, Issue или запись каталога ради пробы.

7. Поддерживай документацию в пределах задачи.
При изменении назначения, структуры, возможностей, платформ, команд, доступов или CI/CD обновляй README затронутого репозитория. Если меняются общие связи, промпты или подготовка участника — обновляй также каталог/документацию Hub и README организации (.github-private/profile/README.md) в пределах задачи. Сверяй инструкции с фактическим состоянием; не объявляй подготовленные настройки работающими. Если README не затронут, укажи это с причиной в PR.
В выделенном личном рабочем каталоге поддерживай WORKSPACE.md; его диагностику
не публикуй в общих README. Если общие README содержат ошибки, подготовь
исправление в соответствующем checkout и обычном PR, сохранив чужие изменения.

8. Дай проверяемый итог.
Покажи созданные/изменённые локальные файлы и ссылки на источники.
Перечисли реально выполненные проверки, аккаунт без секретов, права и ожидающие
приглашения, SHA политик, требования PR и состояние защиты main.
Раздели «готово локально», «подтверждено в GitHub» и «требует действий участника/владельца».
При недостающем доступе продолжи независимую подготовку, не объявляй всё готовым.
Дай следующий шаг: для идеи — промпт cs-core-hub/docs/new-project.md с предпроектным
интервью; для существующего проекта — открыть checkout и начать отдельную ветку.
```

## Какие доступы запрашивать

| Задача | Минимальные права |
| --- | --- |
| Подготовить рабочий каталог | Локальные права на выбранную папку; Read к Standards и Hub |
| Разрабатывать и открывать PR | Write к нужному репозиторию и авторизация своего GitHub-клиента |
| Создать приватный репозиторий | Member с разрешением организации на создание и соответствующими правами клиента |
| Вести планирование | Write в Delivery, доступ к его репозиториям и поддержка Projects у клиента |
| Изменить защиту и доступ участников | Admin конкретного репозитория либо разрешённая делегированная роль; не Owner всей организации по умолчанию |
| Выпустить приложение | Отдельно согласованные права выбранной среды, ограниченный deploy-доступ и CI/CD |

Настройка папки **не выдаёт** GitHub-права, не устанавливает приложения агентов и
не подтверждает подписку. Приглашение принимает участник со своего аккаунта.
Команды, lockfile, тесты и production-права определяются конкретным проектом.

## Когда считать подготовку завершённой

Источники правил доступны и их версии записаны; checkout и несвязанные изменения
сохранены; клиентские входы согласованы; права подтверждены либо блокеры обозначены;
для выбранного проекта известны команды и порядок PR. Без доступных приватных
правил или подтверждения загрузки инструкций результат обозначается частичным.
