# [CS-Core] Standards

Приватный источник общих правил для проектов Clear Solutions, Codex, Cursor, Claude Code и Antigravity. Правила распространяются на создание проектов, GitHub, ревью, тестирование и поставку изменений.

## Обязательный минимум

1. Изменения в `main` поступают только через PR с **одним одобрением**. Прямые push, force push и удаление `main` запрещены; исключений для администраторов и ботов нет.
2. Новые коммиты сбрасывают прежние одобрения. Последнее изменение должен одобрить другой участник. Все замечания в обсуждениях закрыты.
3. `checks` и `security` обязательны; GitHub Actions является ожидаемым источником статусов. Ветка PR проверена относительно актуального `main`.
4. Выпуск выполняется только после CI для конкретного SHA из `main`. Производственные секреты недоступны PR. Проверка здоровья и откат обязательны для сервисов.
5. Документация, воспроизводимый запуск, журнал решений, проверяемые инструкции для AI-агентов и владельцы кода входят в каждый проект.

**Файлы правил сами по себе не включают защиту GitHub.** Настройки применяются и проверяются через API. Для приватных репозиториев организации защита требует GitHub Team или Enterprise. Этот репозиторий нельзя делать публичным ради обхода тарифа.

## Имена репозиториев

Репозитории команды разделены по назначению:

| Префикс | Тип | Примеры |
| --- | --- | --- |
| `cs-core-` | Служебные: правила, координация, скиллы, шаблоны, общая инфраструктура | `cs-core-standards`, `cs-core-hub`, `cs-core-skills` |
| `cs-project-` | Самостоятельные продукты и проекты, включая веб, mobile, desktop, CLI, API и библиотеки | `cs-project-showcase`, `cs-project-sprout-hop` |

Используйте строчные латинские буквы, цифры и одиночные дефисы:
`cs-core-<назначение>` или `cs-project-<назначение>`. Тип определяется ролью репозитория,
а не его стеком: API продукта — `project`, общий шаблон API — `core`.
Новые продукты по умолчанию получают `cs-project-`. Агент уточняет только действительно
неясное назначение, а не заставляет пользователя выбирать префикс для каждого проекта.
Утилита создания проверяет тип до обращения к GitHub; Free не обеспечивает серверный
запрет вручную созданных имён. [Полная схема имён](docs/repository-naming.md).

Приватный `.github-private` — единственное служебное исключение: GitHub требует
это имя для внутренней страницы организации. Его категория в каталоге — `core`.

## Проверки и применение

```bash
make check
make security
# Нужен доступ к GitHub API. Токен передаётся только окружением GH_TOKEN/GITHUB_TOKEN.
python3 tools/github_admin.py audit Clear-Solutions/cs-project-showcase
python3 tools/github_admin.py apply Clear-Solutions/cs-project-showcase
```

`apply` сохраняет существующие сторонние ruleset, объединяет дополнительные требования собственного ruleset и сохраняет его прежний снимок в игнорируемом `work/`. Требования менее строгими не становятся. После записи выполняется чтение фактического состояния. При недоступном тарифе или недостаточных правах команда завершается ошибкой.

`python3 tools/github_admin.py create Clear-Solutions/cs-core-standards` создаёт только новый **приватный** репозиторий, без автоматического README. Затем первоначальная версия загружается в пустой `main`, включается CI и применяется защита. Все дальнейшие изменения — через PR.

Ревьюеры: `elementary1997` и `light2217`. Автор не одобряет свой PR: один из указанных владельцев одобряет PR другого. CODEOWNERS запрашивает ревью, а ruleset обеспечивает число одобрений.

Для репозитория правил CD выпускает архив и SHA-256 manifest в GitHub Actions artifacts после проверенного коммита `main`. Это поставка пакета правил, а не развёртывание приложения. Для приложений применяется отдельный production pipeline из `docs/ci-cd.md`.

Публикация новых проектов: [единое превью, демо и проверка витрины](docs/showcase-publication.md).
